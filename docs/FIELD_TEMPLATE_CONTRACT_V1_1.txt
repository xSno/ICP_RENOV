1. PRINCIPES SÉMANTIQUES
============================================================

1. Les namespaces décrivent le contexte documentaire de rendu.
   Ils ne correspondent pas nécessairement à des tables de stockage.

2. Chaîne de source :

   Fiche maître
   → données de travail du contrat
   → snapshot contractuel
   → snapshot immuable de la révision documentaire

3. Un template n’accède jamais directement à une fiche maître vivante.

4. Les valeurs company.*, client.*, site.* et equipment.* injectées dans une révision
   proviennent du snapshot de cette révision.

5. Une fiche maître peut préremplir un contrat.
   Une modification ultérieure de la fiche maître ne réécrit jamais silencieusement :
   - un brouillon déjà créé ;
   - une révision existante ;
   - un contrat signé.

6. Toute clé canonique doit avoir :
   - un propriétaire métier ;
   - une source ;
   - un type ;
   - une règle d’obligation ;
   - une règle de rendu ;
   - une utilisation documentaire définie.

7. Convention d’obligation :
   REQUIRED
   OPTIONAL
   CALCULATED
   INTERNAL
   REQUIRED_WHEN(<condition déterministe>)

   PORTÉE :
   - REQUIRED et REQUIRED_WHEN(...) expriment la complétude nécessaire à l’opération qui les évalue, notamment le préflight d’une génération officielle ;
   - ces contraintes n’interdisent jamais la persistance d’un DRAFT incomplet ;
   - une fiche maître ou un brouillon peuvent donc être enregistrés avant que toutes les données documentaires requises soient disponibles ;
   - les données société ne sont requises que lorsqu’une version de modèle sélectionnée les exige.

8. Aucune valeur technique brute ne doit être imprimée.
   Les enums et listes utilisent toujours une clé de rendu calculée ou un bloc textuel validé.

9. Une donnée OPTIONAL vide supprime le bloc, la ligne ou le paragraphe complet qui la porte.
   Aucun libellé, ponctuation ou espace orphelin ne doit rester.

10. Le registre est fermé en V1.
    Un placeholder, un bloc ou une boucle non reconnu bloque la mise à disposition du modèle.

11. La syntaxe illustrative reste :
    {{ namespace.field }}

    La syntaxe technique définitive des placeholders, blocs et boucles sera confirmée par le spike.
    Les clés logiques du présent registre, elles, sont indépendantes du moteur retenu.

RÈGLES D’INTÉGRITÉ DU CYCLE DE VIE :
- une nouvelle révision CONTRACT est générée uniquement depuis DRAFT ;
- une génération CONTRACT officiellement réussie fait passer DRAFT → TO_SIGN ;
- corriger un TO_SIGN exige un événement REOPENED_FOR_CORRECTION puis un retour à DRAFT ; ce retour ne crée aucune révision ;
- après SIGNATURE_RECORDED, les données structurantes sont verrouillées et aucune nouvelle Rxx du même contrat n’est créée ;
- une résiliation future conserve SIGNED ou ACTIVE jusqu’à sa date effective, puis produit TERMINATED ;
- une échéance TACIT ne provoque ni renouvellement certain ni EXPIRED automatique : une confirmation explicite reste requise ;
- ABANDONED est réservé aux contrats DRAFT ou TO_SIGN non conclus.

============================================================
16. VALIDATION D’UN MODÈLE AVANT AVAILABLE
============================================================

Le validateur inspecte au minimum :
- corps du document ;
- tableaux ;
- en-têtes ;
- pieds de page ;
- placeholders ;
- blocs conditionnels ;
- boucles ;
- ressources images.

Bloque la mise à disposition :
- placeholder inconnu ;
- placeholder supprimé ;
- bloc inconnu ;
- boucle équipements absente ou invalide lorsqu’elle est requise ;
- instruction éditoriale interdite ;
- marqueur de revue dans un template de production ;
- incohérence document_kind / contract_type_code ;
- régime annoncé hors allowed_client_regimes ;
- version dont les contrôles requis ne sont pas validés ;
- échec du test DOCX/PDF de référence.

Conditions UX avant « Rendre disponible » :
1. Structure contrôlée ;
2. Test DOCX/PDF réussi ;
3. Validation externe du contenu confirmée ;
4. toutes les données société que cette version déclare nécessaires sont présentes dans la configuration locale.

Une version ne peut devenir AVAILABLE si une donnée société qu’elle exige manque.

Seule une version template.version_status = AVAILABLE peut être sélectionnée pour un contrat.

============================================================
17. RENDU STRICT / GÉNÉRATION OFFICIELLE
============================================================

Avant rendu :
- contrat complet selon la version choisie ;
- version AVAILABLE ;
- contract.type_code compatible ;
- client.regime autorisé ;
- données société requises par cette version présentes ;
- au moins un équipement ;
- données dates/prix cohérentes.

Pendant le préflight :
- tous les placeholders doivent être connus ;
- tous les blocs doivent être connus ;
- les boucles doivent être valides ;
- aucune valeur REQUIRED / REQUIRED_WHEN active ne doit manquer.

Pendant le rendu :
- aucun enum interne imprimé ;
- aucun placeholder restant ;
- aucun marqueur de bloc restant ;
- aucun texte éditorial de conception ;
- blocs optionnels supprimés proprement ;
- valeurs françaises formatées de manière cohérente.

Succès officiel d’un document CONTRACT uniquement si :
1. DOCX généré et lisible ;
2. PDF généré et lisible ;
3. contrôles post-rendu réussis ;
4. document CONTRACT, révision Rxx et snapshot enregistrés.

EFFETS RÉSERVÉS À document.document_kind = CONTRACT :
- attribution du numéro officiel lors de la première génération réussie ;
- création de R01, R02… ;
- passage DRAFT → TO_SIGN.

Pour INTERVENTION_SHEET :
- DOCX/PDF peuvent être générés et historisés comme autre document ;
- aucun numéro officiel de contrat n’est consommé ;
- aucune Rxx n’est créée ;
- le statut du contrat n’est pas modifié.

Si le PDF échoue après succès DOCX :
- génération NON officielle ;
- aucune nouvelle révision ;
- aucun nouveau numéro officiel ;
- ancienne révision intacte ;
- temporaires nettoyés ou isolés.

Aucune révision précédente n’est écrasée.

============================================================
18. FORMATAGE DE RENDU
============================================================

Dates :
- format utilisateur/document français explicite ;
- format canonique interne librement choisi par l’implémentation ;
- rendu déterministe.

Montants :
- deux décimales lorsque nécessaire ;
- séparateur décimal français dans le document ;
- symbole monétaire ajouté par le renderer ou le template, jamais dupliqué.

Taux :
- rendu lisible avec symbole % ;
- aucune valeur brute technique.

Durées :
- renderer vers libellé lisible, ex. « 12 mois ».

Listes :
- libellés contrôlés ;
- pas de codes internes.

Texte multiligne :
- texte brut seulement ;
- retours à la ligne conservés ;
- aucun HTML/Markdown interprété.

20. OPTIONS ET ÉLÉMENTS DEFERRED V1
============================================================

Hors V1 :
- indexation automatique de prix ;
- formule d’index complète ;
- tarification par ligne ou équipement ;
- prix additionnel unité intérieure/extérieure ;
- tarification hors zone générique ;
- puissance totale comme règle commerciale ;
- moteur de clauses libre ;
- champs personnalisés ;
- éditeur de placeholders ;
- fusion arbitraire d’annexes ;
- GMAO ;
- signature électronique ;
- contrats multisites ;
- moteur juridique automatique.

============================================================
21. PRODUCT QUESTIONS NON RÉSOLUES PAR CE DOCUMENT
============================================================

PQ-05 — Variantes juridiques finales
Le registre permet les trois régimes mais ne déclare aucune équivalence.
Les allowed_client_regimes de chaque version doivent venir de la validation de cette version.

PQ-06 — Convertisseur PDF officiel
Le registre est indépendant du moteur.
Le spike doit choisir et valider le moteur Windows cible.

PQ-08 — Numérotation réelle
Le cycle d’attribution est défini.
Le préfixe, compteur initial et politique annuelle restent à décider.

PQ-09 — Reprise des contrats existants
Aucun import massif ni logique de migration n’est ajouté ici.

============================================================
22. CRITÈRES D’ACCEPTATION DU REGISTRE
============================================================

Le registre V1.1 est considéré exploitable lorsque :

1. aucune clé obsolète listée en section 19 n’est utilisée par un nouveau template ;
2. client.regime est sourcé du contrat, jamais du client maître ;
3. contract.conclusion_mode est conditionnel selon la version et le contexte validé ;
4. contract.equipment_items est la seule collection ordonnée de rendu des équipements ;
5. equipment.internal_notes et equipment.observations sont séparés ;
6. seules DEEP_CLEANING et DISINFECTION existent comme options incluses V1 ;
7. le délai de dépannage est requis uniquement lorsque le dépannage prioritaire est inclus ;
8. INDEXED n’est pas sélectionnable en V1 ;
9. un modèle TO_VALIDATE n’est jamais utilisable ;
10. seules les versions AVAILABLE sont proposées ;
11. document.signed_revision n’existe plus ;
12. la signature référence document.id via event.document_id ;
13. l’intervention est un document kind séparé, sans numéro officiel, sans Rxx et sans changement de statut ;
14. les requiredness documentaires n’empêchent jamais la persistance d’un DRAFT incomplet ;
15. STANDARD utilise start_date + initial_duration_months pour calculer initial_end_date ; CUSTOM utilise une end_date explicite ;
16. les compatibilités sont confirmées version par version et une version TO_VALIDATE peut avoir zéro régime confirmé ;
17. aucun enum interne n’est imprimé ;
18. un champ optionnel vide supprime son bloc complet ;
19. le numéro n’est attribué qu’après succès documentaire complet d’un CONTRACT ;
20. DOCX réussi + PDF échoué n’est pas un succès officiel ;
21. aucune révision n’est écrasée ;
22. le verrouillage après SIGNATURE_RECORDED empêche toute nouvelle Rxx du même contrat ;
23. un renouvellement confirmé conserve sa période et son prix sans réécrire le pricing initial ;
24. contract.signature_date est une projection calculée depuis SIGNATURE_RECORDED ;
25. aucune Product Question ouverte n’est résolue silencieusement ;
26. le registre reste indépendant du moteur DOCX/PDF.
